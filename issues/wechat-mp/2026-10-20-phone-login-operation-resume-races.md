## 现象

小程序允许静默会话读取数据，写操作弹出手机号登录；成功后刷新账号数据并继续原操作。登录可能合并账号、替换资源列表和会话。独立审查复现两处问题：

1. 用户对资源 A 点击“开始”，登录后 A 消失，页面刷新自动选中默认资源 B。恢复回调直接重调点击处理函数，错误地对 B 发起写入。
2. 编辑面板有未保存排序，点击关闭会保存并触发登录；取消登录回到编辑面板，再点关闭又要求登录。没有放弃草稿的出口，面板一直占用页面，底部导航也无法恢复。

这些是应用的异步状态管理问题，不是微信授权接口本身报错。

## 原因

1. 只保存“重调哪个方法”，没有保存用户原本操作的资源标识和期望结果。登录期间刷新列表会改变当前选中项，或让原状态已经达到目标。
2. 只校验登录成功，未在异步刷新后再次确认会话、页面和组件仍然有效。用户离开页面或会话再次变化时，旧回调可能继续写入。
3. 把编辑面板的关闭与保存绑定，没有设计取消授权后的草稿处理路径。
4. 登录弹层的取消、成功、退场动画、快速重开和组件卸载共享异步回调。若不区分轮次并清理回调，旧取消逻辑可能影响新弹层，或在成功后又执行取消逻辑。

## 解决方案

将登录前的用户意图作为一次有明确目标、成功和取消出口的操作处理。

### 保留原目标，刷新后重新校验

- 在任何乐观变更、业务请求或计时开始之前执行手机号门禁。未登录时先保存资源标识、期望状态和必要草稿。
- 登录成功后，先关闭登录弹层，再用新会话读取账号合并后的数据。不要重放旧账号请求，也不要用旧凭证提交。
- 使用稳定资源标识查找原目标。原目标消失或刷新后的当前选择与原目标不同，提示重选，不自动使用默认资源。
- 对切换状态、收藏等操作保存期望结果，而非仅保存“再切换一次”。刷新后已经达到期望结果时不重复提交。
- 恢复前及每个异步刷新完成后检查宿主仍存活、仍处于原路由、账号可用且会话未再次变化。可把这些检查封装为 canResume；它在登录成功时捕获新会话的标识。

示意代码（资源服务和生命周期检查由应用提供）：

```js
const originalId = currentResource().id
const desiredState = true

requirePhoneLogin(async (canResume) => {
  const latest = await fetchResources()
  if (!canResume()) return
  const target = latest.find(item => item.id === originalId)
  if (!target) {
    showReselectNotice()
    return
  }
  if (target.enabled === desiredState) return
  await setEnabled(originalId, desiredState)
})
```

这里继续的是用户尚未提交、被授权门禁阻止的明确操作。已提交后发生 401 的写请求仍不自动重放。生产系统需要时还应通过服务端幂等或条件更新防止并发重复，不能把一次前端校验视为完整并发控制。

### 给取消登录提供可达的退出路径

- 登录弹层接收独立的成功恢复回调与取消回调。
- 用户取消时，先清除待恢复操作并完成弹层退场，再调用取消回调；不能立刻在仍覆盖页面的登录弹层下弹第二个对话框。
- 有未保存布局的父面板提供“继续调整”和“不保存退出”。前者保留草稿，后者清除待选资源、丢弃本次排序并关闭父面板，恢复它原先隐藏的导航；两者都不发业务写请求。
- 成功登录时清除取消回调；取消时清除成功回调。重复关闭只触发一次取消。
- 快速重开递增动画轮次并作废旧退场任务；组件卸载清除定时器、成功与取消回调。只有同一轮退场完整结束，才允许执行相应后续动作。

### 验证

本次实现通过 288 项自动测试，包含下列回归：

1. 登录后原资源消失：保持空闲，零次开始写入，提示重新选择。
2. 状态刷新后已达到目标：不再反向切换或重复提交。
3. 刷新期间会话变化、宿主卸载或路由切换：旧恢复回调不执行写入。
4. 未保存排序取消登录：可保留草稿继续编辑，也可放弃退出；退出恢复导航，零次布局写入。
5. 取消回调等待完整退场；重复关闭、快速重开、卸载和成功登录不执行过期取消回调。

开发者工具使用真实静默会话验证自动进入首页；业务写入用模拟请求验证登录前零写入、取消无变更、成功后恢复，以及排序面板取消退出。真实手机号授权及后端双边数据合并尚需真机验收。frontmatter 中基础库版本为项目配置声明，不代表本次实际运行时版本已单独采集。
