## 现象

客户端展示由服务端决定的限时状态，用户一直停留前台时，超过 `expiresAt` 后界面仍保留旧状态。只在页面进入或应用重新激活时刷新，无法覆盖持续停留前台的情况。

初版增加到期调度，但仅重试三次：如果这几次离线，或者服务端短暂仍返回同周期有效状态，网络恢复后不会再自动刷新，旧状态可能一直保留到用户手动触发其他刷新。

## 原因

“限制单次退避时长”和“限制总重试次数”是两件事。固定尝试次数耗尽会结束仍然适用的到期任务，既没有成功确认最新状态，也没有保留后续恢复机会。

调度任务还必须绑定账号、权益周期、账号就绪及前台状态。否则旧等待可能在切号、续期或进入后台后唤醒，发起无效请求；仅取消等待任务也不能替代已发请求的结果隔离。

## 解决方案

### 定义上下文与服务端事实源

将账号代际、当前状态的周期/到期时间、就绪及前台标记组成调度上下文。只有当前前台、账号已就绪、存在有效到期时间且需要刷新时才建立等待。

账号、周期或前台条件变化时取消或替换等待；唤醒后和发请求前重新核对上下文。前后台观察回调使用明确的新 phase，不依赖旧 View 闭包里的属性。

到期仅触发现有服务端刷新，不能由本地时钟直接宣布权益失效。成功得到新周期、明确的无效状态或其他不再需要本任务的状态后，由新上下文决定是否重新调度。

### 维持封顶的持续退避

当请求失败，或返回的仍是需要追踪的同周期有效状态，在原上下文仍适用时继续重试。可用 `30 / 60 / 120 / 240 / 300` 秒序列，最后持续保持300秒；它是单次等待上限，不是“五次后停止”。

流程伪代码如下，不是完整可编译实现：

```text
保存当前上下文，等待到期（长等待分块）
退避索引 = 0
只要上下文仍适用：
    再核上下文，尝试从服务端刷新
    若取消、切号、后台、新周期或不再需要刷新：结束
    等待 delays[退避索引]
    退避索引 = min(退避索引 + 1, delays.count - 1)
```

索引始终限制在固定数组内，避免无界失败计数或计算指数溢出。到期时间很远时，长等待可分块为最多一小时，定期检查取消；不要把任意远的 `Date` 一次转换为 `UInt64` 纳秒。

### 等待取消与结果发布分别保护

Swift 的取消是协作式的。取消等待后，不能据此断言所有已发网络请求都停止或不会返回。结果发布处仍要检查账号代际及当前状态版本，避免旧账号或旧周期结果覆盖新状态。新周期到达后应替换旧等待，而不是让旧任务继续针对旧到期时间重试。

### 用可控时间复现恢复缺口

采用可注入时钟/睡眠器及受控 HTTP 响应，不依靠真实等待或随机延时：

| 场景 | 要检查的结果 |
| --- | --- |
| 到期前 | 不提前发刷新 |
| 到期后连续失败超过旧重试上限，再恢复 | 同一有效上下文仍会发下一次刷新 |
| 多次返回旧周期有效状态，之后返回失效状态 | 不提前耗尽重试，最终接受服务端状态 |
| 已达到最大退避 | 后续间隔保持封顶值，不永久停止或不断指数增长 |
| 切号、换周期、后台或不就绪 | 等待取消/替换，旧结果不污染新状态 |
| 很远的到期时间 | 分块等待，不因纳秒转换溢出 |

本次初版在三项确定性回归中出现五处预期失败，修改调度器后转绿；最终定向13项和完整83项测试通过，测试源与提交源的65项文件摘要匹配。这些是可控时间/HTTP替身证据。较早客户端版本的真实购买、恢复、取消和到期观察另列，不能当成新调度器已完成一个完整真机付费周期。
